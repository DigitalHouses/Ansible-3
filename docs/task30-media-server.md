# №30 — Медиасервер (Ansible-3)

## Linux root медиасервера и PBS root@pam — поле №30 (10.11.2026)

В Survey №30 есть необязательное поле типа **secret** `Linux root / PBS root@pam — новый пароль` (`DH_MEDIA_ROOT_PASSWORD_ON_RUN`, target `env`). Введённый пароль применяется нативным Ansible `user` **только к Linux root внутри выбранной VM**, значит он также используется для входа на её PBS как `root@pam`. Не связан с Linux root самого PVE, Samba, Webmin-only администратором или общим паролем медиаприложений. Значение не выводится в логах (`no_log: true`), не сохраняется в site GitHub manifest, ZFS credentials или пользовательском портале. Проверка после применения требует состояния `P` (пароль задан и учётная запись не заблокирована), в отличие от `L`.

- **`apply + keep`:** если пароль указан в №30, задать/сменить его на VM. Если поле пустое, оставить действующий Linux root без изменений, даже если ранее в №05 был сохранён другой пароль.
- **`apply + create/recreate`:** использовать пароль из №30; при пустом поле разрешён резервный вариант — существующий секрет `DH_MEDIA_ROOT_PASSWORD` из №05. Если нет ни одного, остановиться **до** создания/удаления VM с `MEDIA30_ROOT_PASSWORD_REQUIRED_FOR_NEW_VM`, чтобы новый root не остался заблокированным.
- **`audit`:** пароль не применяется. Новый пароль, введённый в Survey №30, действует только для этого запуска и не перезаписывает секрет №05. При последующем `keep` с пустым полем изменений не будет; при будущей переустановке новый пароль нужно снова ввести в №30 либо отдельно обновить №05.

Пароль берётся через защищённый Survey Semaphore, передаётся процессу как переменная окружения, в задачах применяется как SHA-512 crypt hash с `no_log: true`. Никакого Python-кода или открытого пароля в аргументах CLI.

## rclone v1.76.0 + официальный Web GUI (08.11.2026)

№30 устанавливает **официальный pinned Debian amd64 release** rclone v1.76.0 (06.11.2026) напрямую из `downloads.rclone.org` с фиксированным SHA-256, не ограничиваясь устаревающим Debian APT. Задача не создаёт удалённых подключений, не удаляет существующий root `rclone.conf`, не создаёт mounts и не выполняет копирование/восстановление данных.

Встроенный начиная с v1.74 новый `rclone gui` запускается как `dh-rclone-gui.service`, systemd с `User=<owner_slug>` (не root). Постоянный конфиг GUI — `/var/lib/digitalhouses/rclone/rclone.conf`, отдельный от прежнего root rclone; сервер работает с правами владельца Samba (группы media/doc) и не имеет доступа к admin-only backup ZFS. Для работы браузера нужны **два LAN-порта** на IP VM: GUI `5580`, RC API `5572`. Они не публикуются через Cloudflare; создание внешнего административного маршрута требует отдельной задачи Access.

Локальная ссылка на портале: `http://<media-ip>:5580/login?url=http%3A%2F%2F<media-ip>%3A5572%2F`. Пользователь: `mediaadmin`, пароль генерируется один раз (48 hex символов), хранится только внутри VM в `/etc/digitalhouses/rclone-gui.env` (root:root, 0600). Посмотреть из PVE root: `qm guest exec 2232 -- cat /etc/digitalhouses/rclone-gui.env` — **не публиковать вывод**. Пароль не передаётся в аргументах процесса, не логируется (rclone `--log-level ERROR`), не совпадает с коротким паролем медиаприложений. При повторном №30 пароль сохраняется. Встроенная проверка подтверждает GUI HTTP 200, отказ API без логина HTTP 401 и успешный авторизованный `core/version`. Интерфейс rclone API эквивалентен возможностям UNIX-пользователя службы; доступ к обоим портам разрешать только в доверенной локальной сети.

Фактическое развёртывание на VM 2232 должно подтверждаться отдельным запуском №30 в режиме `apply + keep + import` и итоговым `PLAY RECAP`; наличие кода само по себе не означает, что служба уже работает.

## Портал DigitalHouses и многопользовательский доступ (08.11.2026)

- Тёмный портал-витрина: каждая карточка приложения открывает отдельную вкладку (`target="_blank"`, `rel="noopener noreferrer"`). Файлы представлены Filestash/Sambee, без дополнительных верхних карточек.
- SMB-адреса `Media` и `Documents` показаны отдельно для Windows (`\\\\IP\\Share`) и macOS (`smb://IP/Share`). У каждого адреса своя иконка копирования; браузеры на HTTP пользуются безопасным fallback копирования.
- На портале показываем только локальную ссылку на Webmin `https://<media-ip>:10000/` (в новой вкладке). Внешний административный адрес `https://<site-id>-pve-mediaserver-admin.digitalhouses.vip/` продолжает работать через Cloudflare Access, но **не выводится на страницу медиасервера**. Webmin принимает оба Host/Referer и не перенаправляет локальных пользователей на внешний домен.
- Штаты Samba `[Media]` и `[Documents]` теперь принимают членство `@media_group` / `@doc_group`; `DigitalHouses` и `Backups` остаются только для `owner_admin`. Ansible-3 управляет только базовыми владельцем и администратором, не удаляет Webmin-пользователей на повторном запуске.
- Webmin — официальный upstream APT с закреплённым ключом; модульная панель `useradmin` + `samba`, Webmin-only пароль root хранится в guest-only `/etc/digitalhouses/webmin-admin-password` (0600). Синхронизация Unix/Samba при операциях Webmin включается; пароль исходного владельца и root Unix не меняется. Если администрирование Webmin не опубликовано через Cloudflare, внешний доступ отсутствует.
- **Граница ответственности:** никаких изменений исходного кода сторонних агентов и приложений. Публикацию через Cloudflare выполнять только после проверки Access-ограничений и HTTPS origin.

## Упрощение дисковых режимов (07.11.2026)

По решению владельца **не проверяем старые GUID, WWN и серийные номера дисков**.

- `import`: находим единственный SATA-диск за выбранным PCI-контроллером, импортируем существующий `serzhan-pool` по имени. Для новой VM после `create/recreate` разрешён `zpool import -f` (старый hostid); `keep` не требует force. Данные на пуле не стираются.
- `erase`: на том же единственном SATA-диске стираем прежнее содержимое и создаём новый пул без сравнения со старым GUID. Это **уничтожает все данные выбранного диска**.
- По-прежнему запрещено выбирать системный диск VM, несколько дисков за контроллером или контроллер, используемый другой VM. При `recreate+import` до удаления VM проверяется, что старая VM видит пул нужного имени, без GUID.
- Выбранный запуск для serzhan-home: `apply + recreate + import`. Реальное применение через Semaphore пока не подтверждено.

## Режим и два действия в Semaphore (safe defaults)

- VM: keep — существующая проверенная VM; create — только отсутствующая; recreate — удалить только собственную VM и её виртуальные диски, затем единый create.
- Disk: import — импорт существующего ZFS без стирания; erase — стереть только диск за выделенным SATA-контроллером и создать ZFS.

**Параметры CPU в №30 (Survey, PR #42):** два необязательных независимых целочисленных поля `DH_MEDIA_VM_CPU_PERCENT` (общая квота всей PVE VM) и `DH_MEDIA_TRANSCODE_CPU_PERCENT` (общая квота Plex + Jellyfin). Значение `150` означает 1,5 логического ядра; допустимы 25–(cores × 100) процентов. Пустое поле берёт число из приватного site manifest: сейчас `cpu_limit: 1.5` → 150% VM и `transcode_cpu_limit: 1.0` → 100% медиаплееров. Никакого неявного изменения этих настроек при обычном audit: №30 только выводит выбранное значение. В **неопубликованном** `media-server-deploy.yml` PVE лимит передаётся в `qm set --cpulimit`, а для Plex/Jellyfin настроен единый `dhtranscode.slice` с `CPUQuota=N%`; после apply предусмотрено чтение PVE конфигурации и cgroup `cpu.max`. Реальные изменения CPU ещё не проверялись на VM.

Шесть комбинаций — не шесть реализаций. Выбор в Semaphore достаточен как разрешение на действие. Технические проверки обязательны: exact VM, PCI controller, отсутствие чужого VM owner, ровно один физический диск за SATA в госте, исключён системный диск и чужой/multi-vdev ZFS. Import не может переходить в erase по ошибке. Импортируемые пулы не переименовываются.

## Этапы реализации

1. Каноническая site identity, доверенный PVE SSH ключ после №10, точная VM/PCI конфигурация.
2. Штатный Ansible и qm: keep/create/recreate, Debian 13, 2 vCPU, RAM 4096, boot 64 GiB, balloon off, GPU/SATA passthrough из private site manifest.
3. QGA для доверенного SSH ключа guest, только один SATA-диск, native zpool/zfs, declared datasets, директории, автомонтирование. Никаких дополнительных технических approvals.
4. Plex, Jellyfin, qBittorrent, Radarr, Sonarr, Prowlarr, Filestash, Sambee, digitalhouses_plex_agent, локальный портал и авторизация native API/CLI. При необходимости собственного Python сначала отдельное техническое согласование; не копировать старые custom Python tools.
5. SMB shares Media, Documents, Backups, DigitalHouses; Bonjour, Plex autoscan, медиапути, CPU/ARC и GPU. Общий пользовательский пароль 6–8 символов, первичный — 8, без логирования; Plex со своей учёткой. Нельзя открывать смену пароля через незащищённый HTTP.
6. №81 как приёмка внутри №30: VM, QGA, ZFS, GPU, SMB, приложения/логины/порты, библиотека, повторное исполнение.

PBS datastores/backup jobs, PVE backup jobs, legacy NFS cleanup, изменение PVE IP, публикация SMB в Internet, сторонние VM и Cloudflare PVE/Quantum/Semaphore. Media Cloudflare — последующий отдельный этап; новый tunnel или Access не создавать неявно.

## Реализовано в ветке

- Рабочий `playbooks/media-server.yml` (из `main`): читает оба приватных manifest через токен №05, проверяет VM/PVE/PCI и через QGA — ZFS, GUID, datasets, сервисы, реальные download mountpoints; возвращает MEDIA30_AUDIT_ONLY с `changed=0`. В PR сохранён без изменений после merge `origin/main`. Установочные операции находятся только в `playbooks/media-server-deploy.yml`.
- Подготовленный apply-контур (пока не опубликован в main): нативный qm lifecycle для keep/create/recreate, cloud-init/QGA, сверка ED25519 через QGA и SSH, SATA vendor/device/class, ZFS import/erase, datasets, native ZFS boot, QGA/GPU/ARC/swap. `import` теперь **без `-f`**: для активного пула проверяется точный GUID из private manifest, а для отсутствующего выполняется read-only scan только выбранного SATA диска/разделов, проверка уникального name+GUID и импорт **строго по GUID без force**, затем повторная проверка GUID/топологии. Тест `tests/media-import-guard.yml`: правильный/чужой/неоднозначный идентификатор (`ok=3, changed=0, failed=0`). В отличие от старой версии, qm destroy не включает purge backup jobs.
- Гостевая часть: два POSIX/Samba пользователя из site-repo, пароль на ZFS (генерируется только при отсутствии, сохраняется при повторах), четыре закрытых SMB share, Bonjour и локальный портал на 80. Портал публикует собственную SVG-иконку и внизу — команду `qm guest exec` для просмотра текущего пароля **только в PVE Shell**. Не выдаёт пароль через HTTP. Смена общего пароля выполняется на отдельной странице `https://<guest-ip>/account/` через локальный HTTPS и независимый `dh-media-account` Unix-socket backend. Форма требует старый пароль, новый и подтверждение; backend проверяет CSRF, ограничивает попытки, создаёт root-only запрос на ZFS и вызывает исключительно native Ansible №31 для всех служб. `/account/api/` по HTTP 80 всегда недоступен, публичных секретов нет. На клиентском компьютере нужно доверить локальный CA (сертификат не является публично доверенным).
- Windows WS-Discovery (WIP): `wsdd2` привязывается к **фактически обнаруженному LAN-интерфейсу** из `ip -4 route get <gateway>`, сверяет исходный IPv4 с site manifest и рекламирует имя `server-<owner>` из `discovery.netbios_name` (для этого site — `server-serzhan`). Шаблон должен совпадать с `server-` + `site.owner_slug`, быть в нижнем регистре и укладываться в NetBIOS 15 символов без обрезания; старое `MEDIA-SERZHAN` не соответствует новому стандарту. Режим `-w` включает только WSD, не вмешиваясь в системный LLMNR/resolved. Интегрирован в Samba apply, с readback эффективного ExecStart и systemd active. Офлайн-тест `tests/media30-discovery-console.yml`: `ok=6, changed=0, failed=0`. Видимость в Windows Explorer должна быть проверена на реальном Windows-клиенте и не считается доказанной.
- Консоль Proxmox (WIP): `vga=std` из manifest, `serial0=socket`, штатные гостевые `getty@tty1` и `serial-getty@ttyS0`; перед приёмкой проверяются PVE config и активность обеих login-служб. Пароль serial-пользователя не создаётся и не выводится, отдельный Python helper не переносится. Новое подключение serial0 в работающую VM может потребовать штатного power cycle; код **не перезапускает VM самостоятельно ради консоли**. Старый экспериментальный `softdep bochs pre: i915` не переносим без доказанного дефекта. Реальный noVNC/serial login в браузере и shell ещё не подтверждены.
- Native Plex: официальный signed APT источник, системный сервис, Intel render/media group, проверка HTTP identity и доступа к media dataset. Создание только отсутствующих библиотек Фильмы/Сериалы/Музыка штатным `Plex Media Scanner`, определение ID/типа из Plex SQLite только через `sqlite3 -readonly`, проверка результата на диске; существующие библиотеки не перезаписываются. Четыре штатных атрибута Preferences.xml (auto + partial + periodic 900s) через `community.general.xml` с остановкой Plex только при изменении. Не создаём отдельный сканирующий сервис и не трогаем Plex account claim.
- Native Radarr, Sonarr, Prowlarr: checksum-pinned архивы из прежнего media-контракта, сервисы и официальные host-config API. Для fresh install — сначала только loopback, затем Forms+owner credentials и проверка authenticationRequired перед включением LAN. Настроенный чужой пользователь не перезаписывается. **Реальную авторизацию пользователя и совместимость pinned API обязательно проверить live.**
- Native qBittorrent: Debian package, ZFS paths, loopback-only firstboot, password владельца через штатный WebAPI, контроль выключенного LAN bypass, проверка анонимного отказа и входа владельца по LAN. Существующий пароль не сбрасывать при повторном запуске.
- Native Jellyfin: официальный Debian repository, первый запуск с временным systemd loopback policy, штатные Startup/User/Complete API, проверка входа с общим паролем, три библиотеки Movies/TV Shows/Music, запрет перенастройки чужого администратора. Дополнительно — QSV/HEVC только для известного заводского профиля: GPU render node, реальный VA-API Intel под пользователем Jellyfin, отказ при активном ffmpeg, остановка службы только при изменении, сохранение остальных кодеков. `tests/media-jellyfin-qsv.yml` проверяет корректную замену XML и повторный запуск: `ok=10, failed=0`. Проверку фактического транскодирования на GPU ещё нужно выполнить live.
- Native Filestash: штатный бинарный сервис, bcrypt admin-hash от единого пароля только при первой настройке, SMB passthrough к `127.0.0.1` с Go-шаблонами username/password, предварительно сохранённый 16-символьный secret_key, реальная проверка расшифрованного middleware через admin API и наличия SMB login form. Конфигурация существующего сервиса не перезаписывается; чужой backend и неправильный пароль блокируют выполнение.

## Подготовка явного destructive E2E `recreate + erase` (2026-11-06)

Владелец запросил разрушительный запуск №30 для существующей **только** VM `2232` и диска за SATA PCI `0000:2b:00.0`. Аудит #85 подтвердил пул `serzhan-pool`, GUID `40733622006301358`, ONLINE и непустые `media/downloads` и отдельный `downloads` dataset; `erase` уничтожит также документы, резервные копии и все остальные datasets этого пула. **Фактический `recreate + erase` не выполнялся; обновлённый apply допускается только в Draft-коде и ещё не зарегистрирован в Semaphore.**

Подготовлены две независимые проверки перед разрушением: (1) ещё на **старой работающей VM, до `qm shutdown/destroy`**, проверка имени, описания, отсутствия lock, двух PCI devices, QGA, GUID ровно существующего пула, ONLINE, единственного ZFS vdev и отсутствия ошибок; (2) уже внутри новой VM, **до остановки служб, `zpool destroy`, `wipefs`**, повторное сопоставление единственного SATA-диска с исходным именем и GUID по активному пулу либо read-only ZFS label scan. Если диск поменяли между стадиями, выполнение прервётся до стирания. Импорт чужого пула не допускается.

Образ Debian 13 с официальным SHA512 теперь предварительно скачивается на PVE **до удаления старой VM**; в `tasks/media-vm-apply.yml` после `qm destroy` нет повторных сетевых загрузок, а хэш файла проверяется перед `qm importdisk`. Дополнительно `create` отвергается для существующей VM. Private site manifest пополнен обязательной директорией `media/downloads` (PR DigitalHouses/site-serzhan-home#3), иначе первый запуск qBittorrent на пустом ZFS не смог бы стартовать.

**После erase ZFS GUID всегда меняется:** native задача считывает и сообщает новый GUID в журнале. Для следующего `import` потребуется синхронизировать поле `media_vm.storage.import_pool_guid` в приватном site-repo с фактическим новым GUID; нельзя использовать старый GUID молча. Автоматического коммита в private repo во время разрушительного запуска нет.

`tests/media30-recreate-erase-guard.yml` проверяет точное совпадение, чужой и неоднозначный пул (отказы ожидаемы), а также порядок preflight → download → VM lifecycle → disk erase; все проверки выполняются на DEV без изменений гостя. Это не live E2E; после удаления искусственных блокировок реальную корректность установочного пути должна подтвердить встроенная №81.

## Адрес медиасервера — Survey №30 (2026-11-08)

В Semaphore №30 новое текстовое поле `DH_MEDIA_IP` («IP медиасервера»), значение по умолчанию **`232`**. При вводе одного последнего октета адрес рассчитывается из подсети шлюза приватного site manifest: для `192.168.11.1` — `192.168.11.232/24`, для `192.168.22.1` — `192.168.22.232/24`. Допускается и полный IPv4 без `/24`, например `192.168.11.233`. Если site manifest уже содержит нестандартный адрес (например, `.233` после прошлой установки), оставленное значение Survey `232` **сохраняет существующий адрес**; для явного выбора `.232` тогда нужно ввести полный IP. Адрес должен оставаться внутри объявленной site /24, не попадать в DHCP-диапазон и не совпадать с шлюзом либо PVE.

- `audit`: только показывает выбранный IP, **никаких изменений**.
- `apply + create/recreate`: использует выбранный IP при создании VM, настройках гостей и URL; после **успешной** приёмки PVE и медиасервисов фиксирует IP в приватном `site-<id>/inventories/<id>/media_vm.yml` через GitHub API с проверкой SHA исходного файла. Остальные настройки/комментарии YAML сохраняются. Следующие задачи №31–33 получают новый адрес из этого канонического манифеста.
- `apply + keep`: не позволяет незаметно менять IP уже существующей VM. Выбранный адрес должен совпадать с фактическим PVE `ipconfig0`; если не совпадает — fail до любых VM/ZFS изменений.
- Проверяется отсутствие такого же `ipconfig0` в других VM **этого PVE**. Для двух отдельных PVE в одном LAN IP других машин автоматически не обнаруживаются; перед применением пользователь должен назначить реально свободный статический адрес.
- Поле IP **не создаёт вторую VM само по себе**: на том же PVE для второго медиасервера нужны отдельный VMID, имя и дисковый контроллер в отдельном site manifest.

Тесты: `tests/media30-ip-survey.yml` и `tests/media30-ip-manifest-render.yml` — без обращения к инфраструктуре. Регистрация поля в существующем шаблоне Semaphore выполняется штатным каталогом №00. При текущем применении к работающему медиасерверу `keep` с `232` не изменяет его IP.

## PBS 4.2+ на медиасервере (08.11.2026)

В №30 после установки rclone добавлен общий native-блок `tasks/media30-pbs-apply.yml`, который также запускается точечно из уже существующего №33 (`playbooks/media-rclone-gui.yml`) на существующей VM. Это **установка сервера**, а не настройка резервных копий.

- На Debian 13 Trixie amd64 — **только** `proxmox-backup-server` из официального `pbs-no-subscription` APT репозитория. Метапакет `proxmox-backup` **не ставится**: ядро гостя, GPU и ZFS из Debian сохраняются. Публичный Proxmox keyring берётся по HTTPS с официальной SHA256 и применяется как отдельный `Signed-By` без `apt-key`.
- Пакет ставится через native Ansible `apt` (с минимальной версией >=4.2); `dpkg-query` и Ansible `version` требуют **не ниже 4.2**. Проверяются `proxmox-backup.service` и `proxmox-backup-proxy.service`, локальная HTTPS-страница `127.0.0.1:8007`.
- На портале медиасервера появляется ссылка **`https://<media-ip>:8007/`** (LAN, self-signed TLS); штатная учётная запись `root@pam` использует пароль Linux root VM. Credential `DH_PBS_ADMIN_PASSWORD` из №05 пока **не расходуется**, `admin@pbs` отдельно не создаётся; настройка пользователей и API токенов — будущая согласованная задача.
- Не создаются datastore и ZFS dataset/quota, не меняются диски, не настраиваются локальные/облачные PVE backup jobs, нет PBS GC/prune/verify jobs или публикации через Cloudflare. Для однотипной схемы хранения и 70/30 квот потребуется отдельный этап, с сохранением медиа данных.
- На mini-PC со 16 ГБ RAM и медиасервисами PBS будет делить ресурсы. Минимум, рекомендуемый Proxmox для PBS без учёта медиа — 4 GiB RAM и 4 ядра; нагрузку/квоты нужно оценить до использования хранилища в качестве производственного PBS.

Тест: `ansible-playbook tests/media30-pbs.yml`; guest: `qm guest exec <vmid> -- proxmox-backup-manager versions`. Отдельный playbook для этого сервиса не создаётся — используется текущий точечный шаблон №33, а штатное развёртывание №30 включает PBS автоматически.


## Привязка VMID медиасервера к IP (2026-11-09)

Согласно стандарту один media VMID вычисляется как `2000 + последний октет IPv4`. Например, `192.168.11.232 → 2232`, `192.168.11.250 → 2250`, `192.168.22.250 → 2250`. Поле `DH_MEDIA_IP` остаётся прежним; нового Survey поля VMID не требуется.

Реализация №30 подставляет VMID и IP в единый in-memory `media_spec`; после успешного apply/accept меняет в приватном `media_vm.yml` **оба поля атомарно одним GitHub commit (optimistic SHA)**, не трогая другие настройки. В режиме audit никаких изменений. Проверки VMID существующих гостей, PCI ownership и отказа `keep` при несовпадающем IP сохраняются. Назначение нового IP **не перенумеровывает** старую VM и не позволяет двум VM на одном PVE одновременно пробросить один SATA/GPU контроллер. Для двух медиасерверов всё ещё нужны независимые физические ресурсы и декларации.
