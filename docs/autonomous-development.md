# Ansible-3 — автономная разработка, запуск и диагностика

**Версия:** 0.1 (проект на согласование, 03.11.2026)  
**Статус:** архитектурное описание, не разрешение на изменение инфраструктуры.  
**Основной стандарт:** [ANSIBLE_STANDARDS.md](../ANSIBLE_STANDARDS.md).

## 1. Цель

После однократного подключения инструментов ChatGPT самостоятельно выполняет обычный цикл: меняет Ansible-код → проверяет синтаксис/структуру → запускает нужный шаблон через **штатный API Semaphore UI** → получает ID, статус и полный журнал → диагностирует проблему → исправляет код → повторяет до выполнения утверждённых критериев. Пользователю не требуется вручную запускать задачи, копировать журналы или редактировать файлы.

**Ограничение:** автономность относится к уже согласованным задачам и границам изменений. Новые архитектурные решения, работа с неизвестными объектами и разрушительные действия вне ранее одобренной области требуют согласования. Нельзя обещать автономную фоновую работу между сессиями чата без отдельного запланированного механизма.

## 2. Три существующих канала — без нового сервиса

| Канал | Назначение | Способ |
| --- | --- | --- |
| **GitHub** | Создание и изменение общего кода Ansible-3, проверка diff и истории | Подключённый GitHub connector |
| **Semaphore** | Запуск **именно** шаблонов Semaphore, чтение статуса и журнала задания | Официальный REST API по HTTPS и действующий API-token |
| **Linux / файловая система** | Диагностика runner, чтение файлов и service logs, локальные синтаксические проверки, проверка окружения | Подключённый Desktop Commander, независимо от API Semaphore |

Не создавать собственные Python-агенты, root-workers, очереди, демоны, наблюдатели или сервис-синхронизаторы. GitHub остаётся источником кода; не редактировать рабочую копию Semaphore «в обход» Git без специальной аварийной процедуры.

## 3. Контур Semaphore API

Официальный API Semaphore UI документирует, среди прочего:

- `POST /api/project/{project_id}/tasks` — запуск задания с `template_id` и допустимыми параметрами.
- `GET /api/project/{project_id}/tasks/{task_id}` — получение текущего состояния.
- `GET /api/project/{project_id}/tasks/{task_id}/output` — получение журнала.
- `GET /api/project/{project_id}/tasks/{task_id}/raw_output` — исходный вывод, если поддерживается установленной версией.

**Перед первым реальным запуском проверить API-контракт установленной версии** (в пилоте обнаружена Semaphore 2.20.16-beta9). API-токен создаётся штатным способом, хранится только локально в защищённом credential-файле или совместимом стандартном хранилище. Не помещать его в Git, чат и историю команд; не извлекать существующие чужие токены из закрытых файлов для обхода ограничений.

Использовать текущую HTTPS-конфигурацию и штатную проверку сертификата/доверенного CA. Если сертификат не доверен, исправить доверие, а не отключать верификацию как постоянный способ.

**Смысл:** вместо отдельного launcher CLI ChatGPT делает прямой стандартный вызов API с уже разрешённой учётной записью. Само инфраструктурное изменение выполняет штатный Ansible внутри Semaphore.

## 4. Независимый Linux/debug-канал

Через Desktop Commander можно читать файлы и metadata, запускать shell-команды, смотреть процессы, `systemctl`, `journalctl`, `git status`, логи ОС, а также выполнять `ansible-playbook --syntax-check` и `ansible-lint`, если доступны и применимы к задаче.

Linux-доступ **не зависит** от API Semaphore. Он нужен для диагностики среды и безопасных тестов; основной путь изменения управляемой инфраструктуры остаётся Git → Semaphore → Ansible. При необходимости проверки на целевой VM/PVE использовать уже согласованные SSH/API identities и не считать право root разрешением стирать данные.

**Проверенные факты пилота (read-only, 03.11.2026):** Desktop Commander подключён к site runner; команды выполняются как root; `digitalhouses-semaphore.service` запущен; `/opt/ansible/venv/bin/ansible-playbook` существует (ansible-core 2.21.4). API работает через HTTPS на локальном порту 3000. **03.11.2026 подтверждены:** токен в root-only файле (mode 0600), `GET /api/user` — HTTP 200 и `admin: true`; `GET /api/projects` — HTTP 200 (проект `serzhan-home`, ID 1); роль проекта — `owner`; `GET /api/project/1/templates` и `GET /api/project/1/tasks` — HTTP 200; `GET /api/project/1/tasks/18` и журналы задач 18 и 14 — HTTP 200, оба содержат `PLAY RECAP`. Эти факты описывают один проверенный экземпляр, **не являются универсальными настройками для всех сайтов**.

## 5. Цикл работы без ручных действий пользователя

1. Получить согласованную цель, целевые ресурсы и критерий успешной работы.
2. Через GitHub внести минимальное изменение в нужную роль/playbook; определить конкретный commit.
3. Через Linux-канал выполнить подходящие статические проверки без обращения к производственным секретам.
4. Через API Semaphore запустить согласованный шаблон на нужном site с известными параметрами.
5. По task ID получить фактический статус, полный вывод и `PLAY RECAP`. Сопоставить запуск с Git revision и наблюдаемым результатом.
6. При ошибке прочитать конкретные логи системы и целевого ресурса, определить причину, исправить код и повторить шаги 2–5.
7. Сообщить пользователю итог: commit, номер задачи Semaphore, результат, существенные изменения, оставшиеся ограничения.

Не разрабатывать отдельный исполнитель этих шагов: это последовательность действий ChatGPT с использованием **существующих коннекторов**.

## 6. Разрешения и границы автономности

- **Без повторных запросов:** безопасные изменения кода и диагностика, согласованные тестовые операции и запуски в заранее утверждённой области.
- **С отдельным согласованием:** новые требования, архитектурные исключения, уничтожение неуказанных ресурсов/данных, изменение границ доступа.
- **Без обходов:** если API токен, права, сеть или tool-access блокируют запуск, не пытаться «вскрывать» доступ. Сообщить о конкретном недостающем элементе и устранить его штатным способом.
- **Без проверки ради проверки:** проверять только нужные предусловия, фактический результат и возможность корректного повторного запуска.

## 7. Что требуется для ввода в работу (однократно)

1. Подтвердить работоспособность имеющегося Linux-канала — **выполнено**.
2. Настроить штатную авторизацию Semaphore API — **выполнено для read-only операций** (токен admin, роль owner); **POST-запуск задачи ещё не проверен**.
3. Проверить HTTPS trust для локального API и фактические endpoint/response форматы — **выполнено для GET-запросов**; POST-контракт проверяется при пилотном запуске.
4. Проверить, что Semaphore получает код Ansible-3 из GitHub и запускает его с корректными credentials/inventory — **не выполнено**.
5. Указать безопасную пилотную задачу и тестовый ресурс для первого end-to-end запуска — **на согласовании**.

### Критерий приёмки

**PASS**, только если ChatGPT без ручного участия пользователя:
(а) изменил и сохранил тестовый playbook в Git;
(б) запустил его **через Semaphore API**, а не прямой `ansible-playbook`;
(в) получил task ID, статус и журнал;
(г) диагностировал преднамеренную безопасную ошибку через Linux-канал;
(д) исправил её и повторно запустил задачу с успешным фактическим результатом;
(е) подтвердил безопасный повторный запуск.

Если не выполнен хотя бы один этап, автономное управление **не считается настроенным**.
