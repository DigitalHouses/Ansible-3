# Codex — инструкции проекта Ansible-3

## Границы

- Работай только над согласованной задачей в репозитории **DigitalHouses/Ansible-3**. На центральном DEV рабочая копия — `/home/dev/work/ansible-3`, на site runner — `/opt/ansible-3`.
- `ANSIBLE_STANDARDS.md` — основной стандарт. Учитывай разницу между правилами «СОГЛАСОВАНО» и «ПРЕДЛОЖЕНИЕ»; не выдавай предложения за решения владельца.
- Старый `DigitalHouses/dh_ansible` (`/opt/digitalhouses/src`) и действующая инфраструктура не входят в область изменения, если владелец явно не определил иное.
- Не придумывай IP, VMID, названия дисков, пароли, параметры Cloudflare или решения архитектуры. Если существенное решение не согласовано — остановись и обозначь выбор.
- В разных домах LAN-подсети не пересекаются; исключение по совместному размещению — `serzhan-home` и `dh-core` в одной домашней сети владельца `192.168.11.0/24`. Не закладывай перекрытие сетей или дополнительные Virtual Networks без подтверждённой необходимости. См. S24.
- Физические PVE не путать: `serzhan-home / Beelink S12 PVE — 192.168.11.220` и `dh-core / ASRock PVE — 192.168.11.240` (сменён с `.230` 12.11.2026). Изменять IP ASRock только через независимо адресованный/проверенный CORE workflow; HOME Semaphore №10 не является командой на CORE. См. S24.
- Всегда сопровождай конкретный IP/VMID/CTID в объяснениях, документации, отчётах и инструкциях **именем объекта и назначением сервера** (`serzhan-home / Media Server — VM2223, 192.168.11.223`). Не меняй технические machine-readable IDs ради оформления. См. S25.
- Используй штатный Ansible и поддерживаемые коллекции. Не создавай собственный Python, shell-оркестраторы, workers или новые службы без отдельного согласования.

## Рабочий цикл

1. Прочитай относящиеся к задаче файлы и выясни фактический путь от исходников до шаблона Semaphore. **Шаблоны проекта `serzhan-home` (ID 1) могут ссылаться на старый репозиторий; правка Ansible-3 сама по себе их не обновляет.**
2. Реализуй только согласованное изменение. Для Ansible используй подходящие проверки синтаксиса и lint, если инструменты установлены; отсутствие тестов не называй успешной проверкой.
3. На центральном DEV для чтения Semaphore используй **штатный HTTPS REST API** и защищённую конфигурацию `/home/dev/.config/ansible-3/<site>.curl` (инструкция `bootstrap/README.md`). Не читай и не выводи токен, не отключай TLS. Исторический MCP `semaphore` на site runner допустим только если штатно подключён там и настроены подтверждения.
4. Запускай задачи через API или MCP **только когда явно дано задание выполнить конкретный шаблон**, проверено соответствие проекта, шаблона, playbook и репозитория и соблюдены все необходимые подтверждения. Если система заблокировала действие, не обходи блокировку другим каналом.
5. После разрешённого запуска получи ID, дождись окончания через GET статуса/журнала (или штатный `wait_for_task`), прочитай ошибки и `PLAY RECAP`. При ошибке локализуй причину, исправь в надлежащем репозитории и повторяй запуск только в рамках разрешённой задачи и после проверки источника исполняемого playbook.
6. В отчёте различай: **код изменён**, **код проверен локально**, **шаблон запущен**, **результат принят**. Укажи ID запуска, финальный статус, `changed/failed/unreachable`, существенные пропуски и оставшиеся риски.

## Пределы действий

- Не трогай другие VM/LXC, диски, данные, ZFS-пулы, PBS/backup, DNS/Cloudflare и credentials без явной области работ. Удаление или стирание данных всегда требует конкретного разрешения владельца.
- Не меняй настройки безопасности Codex/MCP, не отключай подтверждения и не подменяй Semaphore непосредственным Ansible CLI.
- Не создавай коммиты и не отправляй изменения в GitHub, если действие не входит в утверждённую задачу; показывай итоговый diff.
